# CareerPilot Architecture

This document describes the target architecture and the decisions made so far. Sections
marked _(planned)_ describe design intent for later phases. The database schema is documented
separately in [database.md](database.md).

## 1. System overview

```
 ┌──────────────────────┐      HTTPS/JSON      ┌─────────────────────────────┐
 │  apps/web (Next.js)  │ ───────────────────▶ │     apps/api (FastAPI)      │
 │  UI, auth session,   │                      │  domain services, AI        │
 │  approval screens    │ ◀─────────────────── │  orchestration, automation  │
 └──────────────────────┘                      └──────────────┬──────────────┘
                                                              │ SQLAlchemy (asyncpg)
                                               ┌──────────────▼──────────────┐
                                               │ PostgreSQL + pgvector       │
                                               │ relational data + embeddings│
                                               └─────────────────────────────┘
          External (planned): LLM provider (Claude) · embedding provider · Playwright browser
```

- **Frontend** owns presentation, the user session, and every human-approval interaction.
- **Backend** owns all business logic, persistence, AI calls, and browser automation. The
  frontend never talks to AI providers or the database directly, so API keys stay server-side.
- **One database** for relational data and vectors. pgvector avoids running a separate vector
  store and lets matches be joined with profile and job data in plain SQL.

## 3. Backend design

### Layering

| Layer                       | Responsibility                                      | May depend on       |
| --------------------------- | --------------------------------------------------- | ------------------- |
| `app/api`                   | HTTP: routing, request/response schemas, status codes | services, `core`  |
| `app/<domain>/service.py` _(planned)_ | Business rules for one domain         | repositories, providers |
| `app/<domain>/models.py`    | ORM models + enums (see database.md)                | `app/db`, other domains' models |
| `app/providers` _(planned)_ | AI/embedding provider interfaces + adapters         | `core`              |
| `app/db`, `app/core`        | Infrastructure                                      | nothing app-level   |

Planned domain modules map to the workflow: `profiles` (candidate evidence), `jobs`
(discovery + JD analysis), `matching`, `documents` (resume/cover letter generation, PDF/DOCX
I/O), `verification`, `applications` (approval + tracking), `automation` (Playwright).

### Configuration

`app/core/config.py` defines a single `Settings` object loaded from environment variables and an
optional `.env`. Secrets (`DATABASE_URL`, `ANTHROPIC_API_KEY`) are `SecretStr`, so they never
appear in logs or reprs. `DATABASE_URL` is optional so the API and its unit tests run without a
database; readiness reports `not configured` in that case.

### Database

- **Driver:** `asyncpg` via SQLAlchemy 2 async. (psycopg 3's async mode does not support the
  Windows Proactor event loop that uvicorn uses, so asyncpg is the portable choice.)
- **Engine lifecycle:** created lazily on first use, disposed on app shutdown.
- **Sessions:** `get_session()` FastAPI dependency; one session per request.
- **Migrations:** Alembic, async `env.py` reusing the app engine. Constraint naming conventions
  are set on `Base.metadata` so autogenerated migrations are deterministic.
- **pgvector:** migration `0001` runs `CREATE EXTENSION IF NOT EXISTS vector`. Embedding columns
  use `app.db.vector.EmbeddingMixin` (`vector(1024)` + `embedding_model`, HNSW cosine index).
  The dimension is a schema constant (`EMBEDDING_DIMENSIONS`), not an env var: changing it
  requires a migration and re-embedding. Index strategy (HNSW, cosine) will be
  chosen once real data volumes are known.

### Health checks

| Endpoint            | Purpose   | Touches DB | Failure        |
| ------------------- | --------- | ---------- | -------------- |
| `GET /health`       | Liveness  | No         | n/a            |
| `GET /health/ready` | Readiness | Yes        | 503 + reason   |

Readiness requires both a working connection and the `vector` extension.

## 4. AI provider abstraction _(implemented for resume parsing)_

Business logic depends on small interfaces (Python `Protocol`s), not vendor SDKs.
`app/ai/provider.py`:

```python
class LLMProvider(Protocol):
    name: str
    model: str
    async def complete_json(self, *, system: str, prompt: str,
                            schema: dict[str, Any], max_tokens: int = 16000) -> LLMJsonResult: ...
```

- `AnthropicProvider` is the first adapter. It uses the official `anthropic` SDK with
  structured outputs and `claude-opus-5-5` (`LLM_MODEL`), and turns every failure (API errors,
  refusals, truncation, bad JSON) into `LLMError`.
- `get_llm_provider(settings)` returns `None` when no credentials are configured, so callers
  fall back to non-AI behaviour.
- Providers are injected through FastAPI dependencies, and tests substitute deterministic
  fakes.
- Adding a provider means adding one adapter; no domain code changes.

`app/ai/embeddings.py` applies the same pattern to embeddings. `EmbeddingProvider` exposes
`name`, `model`, `dimensions`, `confidence_thresholds` and `embed(texts, input_type)`. There
are two adapters: an offline hashing embedder (the default, used in tests) and Voyage AI. See
[evidence-retrieval.md](evidence-retrieval.md).

## 5. Evidence and claim traceability _(schema implemented; generation planned)_

This is the core integrity guarantee, so it is designed into the data model from the start:

1. Everything the candidate provides is stored as **evidence items** (e.g. a resume bullet, a
   project description, a certificate), each with a stable ID and source document reference.
2. Generation prompts receive evidence items **with their IDs** and must return structured
   output in which every claim cites one or more evidence IDs.
3. The **claim verifier** rejects any claim with missing or non-existent citations and checks
   that cited evidence actually supports the claim. Unsupported claims are removed or flagged
   for the user; they are never silently kept.
4. Generated documents store their claim → evidence mapping so the user can audit any line.

## 6. Human-in-the-loop and automation safety _(approval guard implemented; automation planned)_

- Applications move through explicit states:
  `draft → ready_for_review → approved → filling → awaiting_submission → submitted`.
  Only a user action can move an application to `approved` or `submitted`. The database
  already rejects any post-approval status without `approved_at`, and any `submitted_at`
  earlier than `approved_at` (see database.md, section "Applications").
- Playwright automation fills forms for an **approved** application and then **stops before the
  final submit**, handing control back to the user. There is no code path that clicks a final
  submit button without a fresh, explicit user confirmation.
- Automation never solves CAPTCHAs, bypasses authentication, or accesses sites whose terms
  prohibit it. Job discovery prefers official APIs and feeds that permit automated access.
- Browser session state is treated as a secret (git-ignored, never logged).

## 7. Authentication _(planned)_

Auth.js (NextAuth v5) in the Next.js app manages sign-in and sessions. The backend will verify a
short-lived token issued for the signed-in user on each request, and every table holding
candidate data will be scoped by user ID. `AUTH_SECRET` is already reserved in
`apps/web/.env.example`.

## 8. Frontend

- Next.js App Router; server components by default, client components only where needed.
- `src/lib/config.ts` is the only place that reads environment variables, and only
  `NEXT_PUBLIC_*` ones, so secrets cannot leak into the client bundle.
- `src/lib/workflow.ts` defines the canonical workflow steps, including which ones are
  human-gated. Tests assert that approval comes before assisted application.

## 9. Quality tooling

| Concern     | Frontend                        | Backend                              |
| ----------- | ------------------------------- | ------------------------------------ |
| Lint        | ESLint (next core-web-vitals)   | Ruff (incl. bandit security rules)   |
| Format      | Prettier (+ Tailwind plugin)    | Ruff format                          |
| Types       | `tsc --strict` (+ `next typegen`) | mypy `--strict` + pydantic plugin |
| Tests       | Vitest + Testing Library        | pytest + FastAPI TestClient          |

Unit tests do not require a database or network. DB-backed tests live in
`tests/integration/` and are skipped unless `TEST_DATABASE_URL` points at a disposable database.
