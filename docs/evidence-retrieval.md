# Candidate Evidence Retrieval (RAG)

CareerPilot retrieves relevant, **verified** candidate evidence when it analyzes a job or
generates application material. Every retrieved item carries a reference back to where it
came from.

```
Candidate profile ─► Evidence chunks ─► Embeddings ─► pgvector ─► Semantic retrieval
  (highlights)        (claim + context)   (provider)    (vector(1024))  (top-k, filters, confidence)
```

Code: `app/ai/embeddings.py` (providers), `app/retrieval/` (indexing and search), and
`app/api/routes/candidate_evidence.py` (API).

## Evidence records

Evidence lives in `candidate_evidence` (see [database.md](database.md)).

| Field | Column / source |
| --- | --- |
| `candidate_id` | `candidate_profile_id` |
| `evidence_type` | `source_type`: project, work_experience, education, certification, achievement, coursework, profile |
| `source_record` | the typed subject FK (`project_id`, `work_experience_id`, …) + `source_resume_id` |
| `factual_content` | `content` (one verbatim claim) |
| `embedding` | `embedding vector(1024)` + `embedding_model` + `embedded_at` |
| `verification_status` | **generated by PostgreSQL** from `confirmed_at` (`verified` / `unverified`), so it can never disagree with it |
| `created_at`, `updated_at` | timestamps |

Evidence is created when the candidate adds a highlight or accepts extracted resume data, so
today all evidence is verified. The `unverified` state exists for future flows (e.g. evidence
awaiting confirmation) and is enforced wherever evidence is retrieved.

## Chunks

Each evidence row is already one atomic claim (at most 2,000 characters), so no further
splitting is needed. The text that gets embedded prefixes the claim with its item, for
example:

```
Project: Multi-Agent Research Assistant
Implemented RAG pipeline using document retrieval and question answering.
```

This lets a query about "Acme" find a bullet under the Acme job even if the bullet doesn't
name the company. Item fields (a project's description, etc.) aren't embedded: only evidence
rows are retrievable, because only they are citable facts.

## Embedding providers (`EmbeddingProvider`)

| `EMBEDDING_PROVIDER` | Model | Notes |
| --- | --- | --- |
| `hash` (default) | `hash-v1` | Deterministic feature hashing of words and word pairs. **Offline and lexical**: similarity means shared words, not meaning. Used as the mock in all tests and for keyless development |
| `voyage` | `voyage-3.5` (`EMBEDDING_MODEL` to change) | Voyage AI semantic embeddings over REST. Needs `VOYAGE_API_KEY`. Documents and queries are embedded with the matching `input_type`, 1024 dimensions, batches of 128 |

Anthropic doesn't offer an embeddings model, and Voyage AI is the provider it recommends. Set
`EMBEDDING_PROVIDER=voyage` for real use. Adding a provider means implementing one class with
`name`, `model`, `dimensions`, `confidence_thresholds` and `embed(texts, input_type)`.

## Indexing

- **Lazy and incremental.** Before every search, evidence with no embedding, or with an
  embedding from a different model, is embedded in batches.
- **Edits invalidate.** Changing a highlight's text clears its embedding, so it is re-embedded
  on the next search.
- **Never mixed.** Search only compares vectors from the current model. Switching providers
  re-embeds everything automatically on the next search.
- `POST /api/candidate/evidence/index` `{candidate_id, force?}` builds or rebuilds the index
  explicitly. `force` re-embeds everything.

## Search

`POST /api/candidate/evidence/search`

```json
{
  "candidate_id": "…",
  "query": "RAG pipeline for question answering",
  "top_k": 5,
  "evidence_type": "project",
  "include_unverified": false,
  "min_similarity": 0.2
}
```

`evidence_type`, `include_unverified` (default `false`) and `min_similarity` are optional.

Response (abridged):

```json
{
  "candidate_id": "…",
  "query": "…",
  "top_k": 5,
  "embedding_model": "voyage-3.5",
  "retrieval_confidence": "high",
  "newly_indexed": 0,
  "results": [
    {
      "evidence_id": "…",
      "candidate_id": "…",
      "evidence_type": "project",
      "factual_content": "Implemented RAG pipeline using document retrieval and question answering.",
      "similarity": 0.71,
      "confidence": "high",
      "verification_status": "verified",
      "source": {
        "record_type": "project",
        "record_id": "…",
        "record_label": "Multi-Agent Research Assistant",
        "origin": "resume_extracted",
        "resume_id": "…",
        "resume_file_name": "priya.pdf"
      },
      "created_at": "…",
      "updated_at": "…"
    }
  ]
}
```

- **Similarity** is the cosine similarity between the query and evidence embeddings.
- **Confidence** labels each result `high`, `medium` or `low` using the provider's thresholds:
  `hash` ≥ 0.45 / ≥ 0.20, `voyage` ≥ 0.60 / ≥ 0.45. These are starting points; calibrate them
  on real data. `retrieval_confidence` is the best result's label, or `none` when nothing
  matched. A low value means the candidate probably has no strong evidence for the query.
- **Source references** point at the owning item (`record_id`, `record_label`), how the
  evidence entered the system (`origin`), and the uploaded resume it came from, if any.
- **Filters** are `evidence_type`, verification status, and `min_similarity`. `top_k` is 1–50.
- **Ownership:** a `candidate_id` that isn't the caller's own profile returns 404.
- **Errors:** 422 for invalid input, and 503 when the embedding service is unreachable or
  misconfigured (e.g. `voyage` without a key).

### Why an exact scan

The query fetches the candidate's rows through the `(candidate_profile_id, source_type)`
B-tree index, filters them, and sorts by exact cosine distance. The HNSW index is deliberately
**not** used here: approximate indexes are scanned *before* metadata filters apply, so a
filtered query can silently return fewer than `top_k` results. One candidate's evidence is
small, so an exact scan is both correct and fast. The HNSW index remains available for future
cross-candidate or job-side searches.

## Only verified evidence for generation

- The search API excludes unverified evidence unless `include_unverified: true` is sent, and
  then marks each result's `verification_status`.
- Application generation must call **`retrieve_verified_evidence(...)`**. It has no option to
  include unverified evidence, and it re-checks every result before returning it.

## Tests

Tests use the `hash` provider (and fakes built on it), so they need no API key.

- **Unit** (`tests/test_embeddings.py`): the hashing embedder (determinism, normalization,
  overlap ranking); the Voyage adapter against a mock HTTP transport (request shape, auth,
  ordering, batching, 401/429/500/wrong dimensions/network errors); provider selection; chunk
  text; confidence labels.
- **Integration** (`tests/integration/test_evidence_search.py`): ranking with source
  references, item context, top-k, type filter, `min_similarity`, verified-only behaviour and
  the generation entry point, the database-derived status, incremental and edit-driven
  re-indexing, model switches, the index endpoint, top-k correctness among 60 other
  candidates' similar rows, privacy, validation, and 503s.
